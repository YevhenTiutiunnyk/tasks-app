# Расписание

*[English version](README.md)*

Личное недельное расписание, в котором задачи не вводятся по полям. Пользователь
надиктовывает фразу — «в среду в 10 врач», «каждый вторник в 8 зал», «перенеси
спортзал на четверг» — Claude превращает её в конкретные операции над
расписанием, операции применяются к базе одной транзакцией, экран обновляется.

Приложение написано под один сценарий: достать телефон, продиктовать, убрать
телефон. Отсюда и решения — от разбора фразы до того, что видно на блоке задачи.

**Распознавания речи в приложении нет.** Строка ввода — обычное текстовое поле.
Надиктовывает пользователь тем, чем привык: автор — приложением Glaido, которое
вставляет распознанный текст в поле; системная диктовка клавиатуры работает так
же. То же и в окне уточнения времени — его поля тоже принимают надиктованный
текст. Не занимаясь речью, приложение остаётся маленьким и не зависит от
аудио-API конкретной платформы.

Next.js 16 · TypeScript · Postgres (Supabase) · Anthropic API · Tailwind · Vitest

## Что здесь может быть интересно

**Модель не ходит в базу.** Между разбором фразы и записью стоит слой проверки
(`lib/validate.ts`): он отбраковывает операции, ссылающиеся на несуществующие
задачи, негодные даты, время вне суток, выдуманные категории. Вывод модели —
такие же непроверенные данные, как ввод из формы, и обращается с ним код
соответственно. Отбракованное не исчезает молча: причина показывается в
интерфейсе, потому что сама модель о ней не знает и бодро отрапортует об успехе.

**Пачка применяется целиком или никак.** `lib/apply.ts` открывает одну
транзакцию на все операции фразы и попутно пишет слепок «как было». Отсюда
кнопка «Отменить» на восемь секунд: откат восстанавливает состояние по слепку,
а не пытается вычислить обратные операции. Обход слепка идёт в обратном
порядке — иначе пачка, дважды тронувшая одну задачу, восстановилась бы
в промежуточное состояние.

**Даты — строки, время — минуты.** Ни одного объекта `Date` в бизнес-логике и в
базе: `'2026-08-06'` и 840 минут от полуночи. Это снимает целый класс ошибок,
где перевод часов или часовой пояс сервера сдвигают задачу на соседний день.

**Повторы раскрываются чистой функцией.** `lib/recurrence.ts` превращает правило
и список исключений в конкретные вхождения без единого обращения к базе, поэтому
покрывается обычными тестами. Правка одного занятия материализует его в
настоящую задачу и добавляет исключение — правило остаётся нетронутым.

**Прямое подключение к Postgres вместо клиента Supabase.** Data API выключен
намеренно: `supabase-js` не умеет настоящих транзакций, а без них откат
превращается в набор запросов, каждый из которых может не долететь.

**Структурированный вывод по схеме zod.** Схема ответа модели и валидатор
живут отдельно (`lib/schema.ts`, `lib/validate.ts`); все поля обязательные и
nullable, потому что структурированный вывод требует всех полей в `required`.

## Как устроено

| Слой | Файлы | Отвечает за |
| --- | --- | --- |
| Арифметика дат | `lib/dates.ts` | Границы недели, дни, отбраковка несуществующих дат |
| Повторы | `lib/recurrence.ts` | Правило + исключения → вхождения; чистая функция |
| Схема и проверка | `lib/schema.ts`, `lib/validate.ts` | Форма ответа модели и отбраковка негодного |
| Применение и откат | `lib/apply.ts` | Транзакция, слепок, откат пачки |
| Обращения к модели | `lib/parse.ts`, `lib/parse-clarify.ts` | Превращают надиктованную фразу в запрос к модели |
| Ключи пользователей | `lib/key-client.ts`, `lib/verify-key.ts`, `lib/user-key.ts` | Собирают клиента на ключе вызывающего, проверяют настоящим запросом, шифруют для хранения |
| Доступ к данным | `lib/db.ts`, `lib/week.ts` | Запросы и сборка недели |
| Недельный отчёт | `lib/report.ts`, `lib/report-run.ts` | Сравнение снимка недели с тем, что вышло; понедельничный запуск на одного человека |
| HTTP | `app/api/*` | Двенадцать роутов: неделя, чеклист, команда, уточнение, отмена, задачи, настройки, ключ, подписка, рассылка, отчёт, вход |
| Экран | `app/page.tsx`, `app/checklist/page.tsx`, `app/report/page.tsx`, `components/*` | Сетка, лента, чеклист, отчёт недели, карточка, строка ввода |

Широкий экран показывает недельную сетку с часовой линейкой, узкий —
ленту дней. Диапазон часов считается по рабочим часам и растягивается под
реальные задачи недели, поэтому пробежка в шесть утра не рисуется поверх шапки.

Когда модель поняла задачу, но не поняла когда — она создаёт её на весь день и
возвращает вопрос. Окно уточнения принимает такой же надиктованный ответ:
«завтра в 8 утра, час».

Каждая задача имеет **горизонт**: день, неделю или месяц. Задача с конкретной
датой («почини принтер в четверг в 10») живёт в недельной сетке на этот день.
Задачи без дня — сформулированные как «почини кран на этой неделе» или
«напиши отчёт в этом месяце» — заводятся надиктовкой и живут на отдельном
экране **Чеклист**, доступном через кнопку в шапке. Такие задачи не появляются
в сетке недели специально: сетка — для расписания по времени, горизонты — для
отслеживания прогресса в периоде.

Задачам чеклиста не шлются напоминания — у них нет времени суток. Если остались
невыполненными, они остаются в своём периоде; автопереноса на следующую неделю
или месяц нет. Не сделано — значит не сделано. Колонка `date` такой задачи
хранит якорь периода — понедельник недели для недельной задачи или 1-е число
месяца для месячной, — чтобы разработчик, заглянувший в базу, понял, почему
задача за «этот месяц» датирована первым числом.

Экран чеклиста делит эти задачи на три секции — «На этой неделе», «На следующей
неделе», «В этом месяце» — по тем же горизонтам, что и выше. Секции «Сегодня» в
нём нет: за «когда» отвечает сетка расписания, и дублировать её чеклисту незачем.

Ссылка «Итоги недели» живёт в шапке самого чеклиста и ведёт на экран `/report` —
на главном экране расписания для неё просто нет места. В понедельник утром, в
час начала рабочих часов этого человека (отдельной настройки нет — час берётся
из тех же рабочих часов, что и расписание), приходит пуш с итогами прошедшей
недели: сколько сделано, перенесено и не сделано. Нажатие открывает `/report`;
напоминание о задаче по-прежнему открывает расписание.

За этим стоит снимок, а не сравнение на лету. В понедельник утром задачи
текущей недели записываются как «запланировано»; через неделю, перед самой
отправкой, тот же снимок сравнивается с тем, что стало с этими задачами к
этому моменту, — так получаются «сделано», «перенесено», «не сделано».
Перенесённой задача считается только если ушла из недели целиком — на другую
неделю или в чеклист без дня; сдвиг часа или дня внутри той же недели
переносом не считается. Если на неделе не было запланировано ничего, отчёт не
отправляется вовсе — тишина, а не пуш «0 из 0».

Хранится это в одной таблице, `week_snapshots` (`user_id`, `week_start`), и в
её колонке `reported_at`: роут отчёта отправляет только тот снимок, где
`reported_at` ещё пуст, и сразу же его проставляет. Планировщик здесь тот же
самый, что и у напоминаний о задачах, — раз в минуту (`app/api/notify/route.ts`);
без этой отметки он рассылал бы один и тот же отчёт на каждой минуте после
часа доставки.

## Тесты

```bash
npx vitest run                                                   # без базы: тесты, ходящие в неё, пропускаются
node --env-file=.env.local ./node_modules/vitest/vitest.mjs run   # всё: 309 проходит, 14 пропущено
```

Тесты, ходящие в базу (`lib/db.test.ts`, `lib/apply.test.ts`, `lib/ownership.test.ts`,
`lib/allowed-emails.test.ts`), работают против одноразового Postgres в Docker —
никогда против боевой базы. Уборка в каждом из них адресная — по идентификатору
владельца или по тестовым zz-адресам на `.invalid`, — поэтому указать не ту базу
здесь было бы ошибкой, но не разрушительной: `vitest.setup.ts` вообще откажется
стартовать, если `DATABASE_URL` задана, а `TEST_DATABASE_URL` не указывает
на петлевой или частный адрес, так что такую ошибку и совершить-то не получится.

```bash
scripts/test-db.sh   # пересоздаёт контейнер tasks-test-db на порту 55432
```

Скрипт идемпотентен: контейнер каждый раз сносится и поднимается заново, поэтому
недомигрированная тестовая база — никогда не состояние, которое разбирают
руками, а состояние, из которого просто перезапускают скрипт. Схема никогда не
копируется с боевой базы и не пишется руками — скрипт прогоняет настоящие файлы
из `supabase/migrations/` по порядку, тем же способом, каким собрана схема
боевой базы, поэтому миграция, применённая только к одной из двух баз,
проявится тестом, а не останется незамеченной.

Добавить в `.env.local`:

```
TEST_DATABASE_URL=postgresql://postgres:testpass@127.0.0.1:55432/tasks_test
```

`vitest.setup.ts` выполняется раньше собственных импортов любого тестового
файла и подменяет `DATABASE_URL` на `TEST_DATABASE_URL` — это обязано случиться
раньше импорта `lib/db.ts`, потому что он открывает пул подключений на уровне
модуля, а не лениво. Тот же файл отказывается запускаться вовсе, если
`DATABASE_URL` задана, а `TEST_DATABASE_URL` — нет, не разбирается как адрес
или ведёт не на петлевой и не на частный адрес: потерянная или неверная
тестовая переменная падает громко, а не тихо утекает в боевую базу.

Главное условие намеренно не «отличается от боевого», а «на этой машине или
в её частной сети». Сравнению с боевым адресом доверять нельзя: одна и та же
база Supabase выдаётся под двумя разными именами хостов — напрямую
`db.<ref>.supabase.co:5432` и через пулер
`aws-0-<регион>.pooler.supabase.com:6543`, — и оба адреса лежат рядом в панели
проекта, так что вписать «другой» в `TEST_DATABASE_URL` — самая правдоподобная
ошибка из всех. Боевой адрес публичный по определению и не проходит проверку
на петлевой или частный ни в какой записи. Вторым условием обе строки всё же
разбираются и сравниваются по хосту и имени базы (порт игнорируется намеренно:
5432 и 6543 — две двери в одну и ту же базу Supabase).

Тесты применения и отката работают против настоящего Postgres, а не против
моков: проверяется состояние таблиц после транзакции и после отката. Postgres
при этом локальный, в контейнере, — полный прогон занимает 2,4–2,5 секунды.
Поднятый лимит на тест в `vitest.config.ts` остался с тех пор, когда эти тесты
ходили в боевую базу по сети, и держится теперь как запас на холодный
контейнер: это потолок, а не задержка.

Отдельно лежат семь живых примеров разбора фраз. Они обращаются к настоящему
API, стоят денег и по умолчанию пропускаются:

```bash
RUN_LLM_TESTS=1 node --env-file=.env.local ./node_modules/vitest/vitest.mjs run lib/parse.examples.test.ts
```

Именно они однажды показали, что промпт противоречит замыслу: правило запрещало
создавать задачу без указания дня, а окно уточнения задумывалось ровно для
этого случая.

## Локальный запуск

Миграции применяются в два захода, а между ними — первый вход. Это не причуда
инструкции, а свойство `0004_ownership.sql`: фаза 1 начинается с предохранителя,
который отказывается работать, если в таблице `"user"` не ровно одна строка, и
заполняет новые колонки владельца из `(select id from "user")`. На свежей базе
эта таблица пуста, пока никто не вошёл, — значит, миграция идёт после первого
входа, а не до него.

1. `npm install`
2. Скопировать `.env.local.example` в `.env.local` и заполнить.
3. Применить в SQL-редакторе Supabase первые три миграции из
   `supabase/migrations/` по порядку: `0001_init.sql`, `0002_push.sql`,
   `0003_auth.sql`. На этом остановиться — `0004_ownership.sql` идёт шестым
   шагом.
4. Вписать свой адрес Google в белый список, в нижнем регистре — без этой
   строки не войдёт никто, и страница входа о причине не скажет:

   ```sql
   insert into allowed_emails (email) values ('you@example.com');
   ```

5. `npm run dev`, открыть приложение и войти через Google. Так появится строка
   в `"user"`. Само расписание пока не работает — колонок владельца и таблицы
   `user_settings` ещё нет, — и на этом шаге так и должно быть.

   ⚠️ Между этим шагом и следующим приложение лучше никому не показывать.
   Строка в `"user"` заводится при **любой** попытке входа через Google, в том
   числе у того, кого белый список не пустил: проверка допуска стоит на
   создании сессии, то есть уже после того, как Better Auth завёл пользователя
   (`lib/auth.ts`, `databaseHooks.session.create.before`). Сессии чужой не
   получит, а строку оставит — и предохранитель фазы 1 честно откажется
   работать: «Ожидалась ровно одна строка в "user", найдено 2». Лечится
   удалением лишних строк до применения миграции (сессии и привязки провайдера
   уйдут каскадом):

   ```sql
   delete from "user" where email <> 'you@example.com';
   ```

6. Применить **фазу 1** из `0004_ownership.sql`: всё от начала файла до её
   `commit;`. Она добавляет колонки `user_id`, приписывает существующие строки
   единственному найденному в `"user"` пользователю и создаёт `user_settings`.

   Фазы 2 и 3 ниже по файлу закомментированы намеренно и такими здесь и
   остаются: фаза 2 переносит старую однострочную таблицу `settings`
   в `user_settings`, фаза 3 добирает строки, которые успел записать код без
   владельца, пока он ещё был выложен. На свежей базе нет ни того, ни другого —
   поэтому и `scripts/test-db.sh` прогоняет только фазу 1.

7. Перезагрузить приложение — расписание работает, и всё, что в нём заводится,
   принадлежит вашему пользователю.

| Переменная | Что это |
| --- | --- |
| `ANTHROPIC_API_KEY` | Только для платных тестов разбора фраз (`RUN_LLM_TESTS=1`). Само приложение использует свой ключ каждого пользователя, введённый в настройках |
| `KEY_ENCRYPTION_KEY` | 32 случайных байта в base64 (`openssl rand -base64 32`). Шифрует ключи Anthropic пользователей при хранении. Потеря означает, что все вводят свой ключ заново |
| `DATABASE_URL` | Транзакционный пулер Supabase, порт **6543** |
| `BETTER_AUTH_URL` | Базовый адрес приложения, нужен для колбэков OAuth |
| `BETTER_AUTH_SECRET` | Случайная строка от 32 символов, использует Better Auth |
| `GOOGLE_CLIENT_ID` | ID OAuth-клиента из Google Cloud Console |
| `GOOGLE_CLIENT_SECRET` | Секрет OAuth-клиента из Google Cloud Console |

Ключ каждого пользователя вводится в настройках и хранится зашифрованным
(`aes-256-gcm`, id владельца добавлен в дополнительные аутентифицированные
данные — шифротекст, перенесённый в чужую строку, просто не расшифруется);
на клиент он не возвращается никогда, даже усечённым.

Потеря `KEY_ENCRYPTION_KEY` не даёт собственного видимого симптома: главный
экран продолжает показывать строку ввода (`hasKey` проверяет только то, что
шифротекст записан, и ничего не расшифровывает), а настройки продолжают
показывать «Ключ заведён» — единственный сигнал — отказ при разборе любой
фразы. Починки на сервере нет; каждому надо зайти в настройки и нажать
«Заменить», чтобы ввести ключ заново.

Вход — через Google OAuth силами Better Auth (`lib/auth.ts`); сессию получают
только адреса из таблицы `allowed_emails` (`lib/allowed-emails.ts`). Список
перепроверяется на каждом запросе в `proxy.ts`, а не только при создании
сессии: убранный адрес перестаёт работать сразу, и сессии человека снимаются
со всех устройств разом. Уведомления тоже прекращаются — планировщик работает
вне прокси, поэтому соединяется с той же таблицей сам. Больше ничего не
удаляется: вернули адрес — всё на месте.

Порт важен: на прямом соединении (5432) serverless-функции исчерпают лимит
подключений. По той же причине пул создаётся с `prepare: false` — транзакционный
пулер не поддерживает подготовленные выражения.

Перед выкладкой:

```bash
npx tsc --noEmit && npx eslint . && npm run build
```

## Выкладка

Развёрнуто на Vercel. `vercel.json` сажает функции в `fra1` — рядом с базой в
eu-central-1: один запрос разбора фразы делает больше пятнадцати обращений к
базе, и через Атлантику это добавляло бы около секунды на пустом месте.
